# api-gateway — Integration Contract

## 1. Inbound APIs

The `api-gateway` is a pass-through edge; it does not define its
own domain APIs. The contracts in this section are the
**infrastructure** endpoints the gateway exposes directly, plus
the aggregate behavior of every downstream API the gateway
proxies. The full per-endpoint contracts of every downstream
service are in their own `INTEGRATION.md`; the gateway's role
is to enforce the platform-wide rules (auth, headers, rate
limits, error envelope, audit) consistently.

### 1.1 `ANY /v1/{service}/{resource}`

- **Purpose**: forward to the matched downstream service.
- **Auth**: Bearer JWT (required roles per route; audience per
  service client id; see `architecture/KEYCLOAK_ARCHITECTURE.md`).
- **Idempotency**: forwarded `Idempotency-Key` header.
- **Request**: any body accepted by the downstream service;
  body size limit is per-route (default 1 MiB).
- **Response (varies)**: per the downstream service.
- **Errors** (envelope normalized by gateway):
  - 400 `VALIDATION_FAILED`
  - 401 `UNAUTHENTICATED` (`TOKEN_INVALID` | `TOKEN_EXPIRED` |
    `TOKEN_REVOKED`)
  - 403 `FORBIDDEN` (`USER_SUSPENDED` | `USER_DISABLED`)
  - 404 `NOT_FOUND`
  - 409 `CONFLICT`
  - 413 `PAYLOAD_TOO_LARGE`
  - 422 `BUSINESS_RULE_VIOLATION`
  - 429 `RATE_LIMITED` (with `Retry-After`)
  - 502 `DEPENDENCY_UPSTREAM_FAILURE`
  - 503 `CIRCUIT_OPEN` / `SERVICE_UNAVAILABLE`
  - 504 `DEPENDENCY_TIMEOUT`
- **Validation**: JSON Schema per the downstream service; the
  gateway only checks size and content-type. The downstream
  service is the source of truth for body validation.

### 1.2 `GET /openapi.json`

- **Purpose**: aggregate OpenAPI 3.1 document for every public
  endpoint the gateway proxies.
- **Auth**: none (public).
- **Response (200)**:

  ```json
  {
    "openapi": "3.1.0",
    "info": {
      "title": "Platform API",
      "version": "2026-07-29",
      "description": "Aggregated OpenAPI for the platform."
    },
    "servers": [
      { "url": "https://api.example.com", "description": "production" }
    ],
    "components": {
      "securitySchemes": {
        "bearer": { "type": "http", "scheme": "bearer", "bearerFormat": "JWT" }
      }
    },
    "paths": { "...": "..." }
  }
  ```

- **Errors**:
  - 500 `INTERNAL_ERROR` (aggregate failed)
- **Notes**: the document is regenerated by a CI job on every
  downstream service release. The gateway serves the static
  artifact from a versioned blob.

### 1.3 `GET /docs`

- **Purpose**: Swagger UI for the aggregate OpenAPI document.
- **Auth**: none (public). Optional `?api_key=` for partner
  customers using an embedded view.
- **Response (200)**: HTML page.

### 1.4 `GET /health`, `GET /ready`, `GET /started`

- **Purpose**: K8s probes (see `architecture/OBSERVABILITY.md`).
- **Auth**: none.
- **Response (200)**:

  ```json
  {
    "status": "ok",
    "version": "1.42.0",
    "uptime_s": 1234
  }
  ```

- **Errors**: `/ready` returns 503 with `code: "NOT_READY"` if
  any downstream readiness check fails or if the JWKS cache is
  empty.

### 1.5 `POST /admin/reload` (internal, `127.0.0.1` only)

- **Purpose**: force a hot-reload of the in-process configuration.
- **Auth**: mTLS + client certificate restricted to SRE/CI.
- **Request**:

  ```json
  { "config_keys": ["gateway.routes", "gateway.rate_limits.default"] }
  ```

- **Response (200)**:

  ```json
  { "reloaded": true, "version": 4231 }
  ```

- **Errors**:
  - 400 `VALIDATION_FAILED` (unknown `config_keys`)
  - 500 `INTERNAL_ERROR` (reload failed; previous config retained)

## 2. Outbound APIs

The gateway makes a small number of outbound calls.

| Target | Method | URI | Purpose | Timeout | Retry | Circuit |
|--------|--------|-----|---------|---------|-------|---------|
| Keycloak | GET | `/realms/{realm}/.well-known/openid-configuration` | OIDC discovery (refreshed on rotation) | 2s | 3, exp backoff | yes |
| Keycloak | GET | `/realms/{realm}/protocol/openid-connect/certs` | JWKS | 2s | 3, exp backoff | yes |
| Keycloak | POST | `/realms/{realm}/protocol/openid-connect/token/introspect` | token introspection for partner B2B | 2s | 2, no retry on 4xx | yes |
| `identity-service` | GET | `/v1/identities/introspect` | internal introspection helper (cache-miss path) | 500ms | 2 | yes |
| Downstream services (×50) | ANY | per route | forwarding | 30s (per route) | 0 (downstream owns retry) | yes (per upstream) |
| Redis | various | n/a (Redis protocol) | revocation set, rate-limit counters, JWKS cache | 100ms | 1 | yes |
| Kafka | producer | n/a (Kafka protocol) | `audit.api.request.v1` publish | 5s (acks=all) | 3, exp backoff | yes |

## 3. Produced Events

### 3.1 `audit.api.request.v1`

- **Producer**: `api-gateway`.
- **Topic**: `audit.api.request`.
- **Trigger**: every authenticated request whose JWT validation
  succeeded (sample ratio is configurable; default 1.0).
- **Schema version**: 1.
- **Partition key**: `correlation_id` (so a single end-to-end
  flow is ordered on the audit topic; alternative partitioning
  by `user_id` is allowed for high-volume tenants).
- **Consumers**: `audit-service`, ``reporting-service` (data lake)`.
- **Schema**:

  ```json
  {
    "event_id": "01HZX9C8W6K0G3V2Y5N1Q4R7PB",
    "event_name": "audit.api.request.v1",
    "occurred_at": "2026-07-29T10:42:11.183Z",
    "schema_version": 1,
    "producer": "api-gateway",
    "tenant_id": "global",
    "correlation_id": "01HZX9C7T0XK2P9F0V6E4B1MZA",
    "causation_id": null,
    "aggregate_type": "ApiRequest",
    "aggregate_id": "01HZX9C7T0XK2P9F0V6E4B1MZA",
    "data": {
      "user_id": "01HZX…",
      "user_type": "customer",
      "method": "POST",
      "route": "/v1/rides",
      "matched_route_id": "ride-request.create",
      "upstream": "`trip-service` (ride-request)",
      "upstream_status": 201,
      "status": 201,
      "latency_ms": 142,
      "client_ip": "203.0.113.0/24",
      "user_agent_hash": "5e9c8e1f0b2a4d3e8f1a2b3c4d5e6f70",
      "body_sha256": "9b1f…",
      "rate_limited": false,
      "circuit_open": false
    }
  }
  ```

- **Retry**: 3 attempts with exponential backoff (250 ms, 500 ms,
  1 s). Producer acks = all.
- **DLQ**: `audit.api.request.dlq`. Retention 30 days.

### 3.2 `gateway.config.reloaded.v1`

- **Producer**: `api-gateway`.
- **Topic**: `platform.gateway.config.reloaded`.
- **Trigger**: a successful hot-reload (via event or admin port).
- **Schema version**: 1.
- **Partition key**: `config_version`.
- **Consumers**: ``reporting-service` (data lake)` (low-volume).
- **Schema**:

  ```json
  {
    "event_id": "01HZX9C8W6K0G3V2Y5N1Q4R7PB",
    "event_name": "gateway.config.reloaded.v1",
    "occurred_at": "2026-07-29T10:42:11.183Z",
    "schema_version": 1,
    "producer": "api-gateway",
    "tenant_id": "global",
    "correlation_id": "01HZX9C7T0XK2P9F0V6E4B1MZA",
    "aggregate_type": "GatewayConfig",
    "aggregate_id": "config:4231",
    "data": {
      "config_keys": ["gateway.routes", "gateway.rate_limits.default"],
      "config_version": 4231,
      "trigger": "event",
      "result": "ok"
    }
  }
  ```

- **Retry**: 3 attempts with exponential backoff.
- **DLQ**: `platform.gateway.config.reloaded.dlq`.

### 3.3 `gateway.rate_limit.exceeded.v1`

- **Producer**: `api-gateway`.
- **Topic**: `platform.gateway.rate_limit.exceeded`.
- **Trigger**: a request is rejected with `429
  RATE_LIMITED` (per-route, per-token, or per-IP).
- **Schema version**: 1.
- **Partition key**: `route` (so all rejections for
  the same route are ordered for analytics).
- **Consumers**: ``reporting-service` (data lake)`,
  `fraud-risk-service` (anomalous traffic patterns),
  `audit-service` (rate-limit rejections are audited).
- **Schema**:

  ```json
  {
    "event_id": "01HZX9C8W6K0G3V2Y5N1Q4R7PB",
    "event_name": "gateway.rate_limit.exceeded.v1",
    "occurred_at": "2026-07-29T10:42:11.183Z",
    "schema_version": 1,
    "producer": "api-gateway",
    "tenant_id": "global",
    "correlation_id": "01HZX9C7T0XK2P9F0V6E4B1MZA",
    "aggregate_type": "RateLimit",
    "aggregate_id": "route:ride-request.create",
    "data": {
      "route": "ride-request.create",
      "principal_type": "token" | "ip",
      "principal_id": "01HZX…" | "203.0.113.0/24",
      "limit": 100,
      "window_seconds": 60,
      "retry_after_seconds": 12,
      "client_ip": "203.0.113.0/24",
      "user_agent_hash": "5e9c8e1f0b2a4d3e8f1a2b3c4d5e6f70"
    }
  }
  ```

- **Retry**: 3 attempts with exponential backoff.
- **DLQ**: `platform.gateway.rate_limit.exceeded.dlq`.
- **Note**: the rate-limit event is emitted on
  best-effort basis; the synchronous 429 response
  to the client is not blocked on the emit. If the
  emit fails after retries, the rejection is
  still recorded in the gateway's
  `gateway_rate_limit_rejections_total` metric.

### 3.4 `gateway.circuit_breaker.opened.v1`

- **Producer**: `api-gateway`.
- **Topic**: `platform.gateway.circuit_breaker`.
- **Trigger**: a per-upstream circuit breaker
  transitions to the `open` state.
- **Schema version**: 1.
- **Partition key**: `upstream`.
- **Consumers**: ``reporting-service` (data lake)`,
  `notification-service` (page SRE on critical
  upstream), `audit-service`.
- **Schema**:

  ```json
  {
    "event_id": "01HZX9C8W6K0G3V2Y5N1Q4R7PB",
    "event_name": "gateway.circuit_breaker.opened.v1",
    "occurred_at": "2026-07-29T10:42:11.183Z",
    "schema_version": 1,
    "producer": "api-gateway",
    "tenant_id": "global",
    "correlation_id": "01HZX9C7T0XK2P9F0V6E4B1MZA",
    "aggregate_type": "CircuitBreaker",
    "aggregate_id": "upstream:identity-service",
    "data": {
      "upstream": "identity-service",
      "previous_state": "half_open",
      "new_state": "open",
      "failure_count": 5,
      "window_seconds": 10,
      "reset_after_seconds": 30
    }
  }
  ```

- **Retry**: 3 attempts with exponential backoff.
- **DLQ**: `platform.gateway.circuit_breaker.dlq`.

## 4. Consumed Events

### 4.1 `identity.session.revoked.v1`

- **Producer**: `identity-service`.
- **Reason**: a Keycloak session was revoked (logout, theft,
  forced revocation). The token's `jti` may still be
  cryptographically valid until `exp`; the gateway must reject
  it.
- **Handler**: write `gateway:revoked:jti:<jti>` to Redis with
  `EX <remaining_ttl>` computed from the event's `exp` field.
- **Deduplication**: Redis `SET` is idempotent on the same key.
  An inbox keyed by `event_id` is maintained in-process for
  audit.
- **Retry**: 3 with backoff (1 s, 2 s, 4 s).
- **Failure**: DLQ `identity.session.revoked.dlq`. An on-call
  alert fires if the DLQ depth > 0 for > 1 min.

### 4.2 `identity.user.suspended.v1`

- **Producer**: `identity-service`.
- **Reason**: a user was suspended (admin, fraud, payment
  failure). The user must be denied at the edge for current
  and future tokens.
- **Handler**: write `gateway:revoked:sub:<kc_sub>` with value
  `suspended` and TTL 30 days. The gateway's revocation
  lookup on every request now includes the suspended-sub set.
- **Deduplication**: idempotent Redis `SET`; an event_version
  is recorded to refresh the TTL on repeated events.
- **Retry**: 3 with backoff.
- **Failure**: DLQ; alert on sustained DLQ depth.

### 4.3 `identity.user.disabled.v1`

- **Producer**: `identity-service`.
- **Reason**: a user is permanently disabled (compliance,
  legal hold). The gateway must reject all current and future
  tokens.
- **Handler**: write `gateway:revoked:sub:<kc_sub>` with value
  `disabled` and TTL 30 days. The disabled value takes
  precedence over `suspended` in the lookup.
- **Deduplication**: idempotent.
- **Retry**: 3 with backoff.
- **Failure**: DLQ; alert.

### 4.4 `configuration.updated.v1`

- **Producer**: `configuration-service`.
- **Reason**: the gateway's configuration (routes, rate limits,
  CORS, error mapping, JWKS refresh interval, audit sample
  ratio) has changed.
- **Handler**: read the new value of every `gateway.*` key from
  `configuration-service`, build an atomic in-memory snapshot,
  and swap the active config atomically.
- **Deduplication**: in-process version stamp; an event whose
  `config_version` is not greater than the current one is a
  no-op.
- **Retry**: 3 with backoff.
- **Failure**: DLQ; the previous config is retained.

## 5. Reliability

- **Timeouts**: upstream 30 s (per-route override); Redis 100 ms;
  Kafka 5 s.
- **Retries**: outbox is not used (no DB). Producer-side retries
  for the audit topic; consumer-side retries for the four
  consumed events.
- **Circuit breakers**: per upstream, per Redis operation, per
  Keycloak call. Default open after 5 failures in 10 s; reset
  after 30 s with a half-open trial.
- **Bulkheads**: per upstream concurrency cap (default 1024) via
  in-process semaphore; per-route body size limit; per-route
  request rate limit.
- **Outbox**: not applicable (no DB).
- **Inbox**: in-process, per consumer, keyed by `event_id`,
  TTL 24 h. Persisted only in the process's memory; on crash,
  Kafka redelivery + idempotent Redis writes provide the
  correct end state.
- **DLQ**: one DLQ per topic. Retention 30 days.
- **Reconciliation**: a daily job in `reporting-service`
  compares the audit topic's per-day event count against
  the gateway's `gateway_audit_events_emitted_total` metric
  for the same window; a mismatch opens a ticket.

## 6. Request id (correlation)

The gateway is the **canonical root** of the platform's per-request
id. The contract is codified in
[ADR-0019](../../architecture/adrs/0019-request-id-at-the-edge.md);
this section is the gateway's implementation of that contract.

`X-Request-Id` and `X-Correlation-Id` are **aliases** — clients may
send either, the gateway prefers `X-Request-Id` if both are sent,
and the response, the audit event, the OTel span, and every
log line in the request scope all carry the same value.

| Stage | Behaviour |
|---|---|
| Inbound | Read `X-Request-Id`; if absent, read `X-Correlation-Id`; if both absent, generate a UUIDv7. If both are sent, use the value of `X-Request-Id`. |
| Response | Set `X-Request-Id` AND `X-Correlation-Id` to the same value. |
| Outbound HTTP | Add `X-Request-Id` AND `X-Correlation-Id` to every call to a downstream service (via outbound interceptor). |
| Outbound Kafka | Set Kafka headers `X-Request-Id` AND `X-Correlation-Id` on every event the gateway produces (`audit.api.request.v1`, `gateway.config.reloaded.v1`, `gateway.rate_limit.exceeded.v1`, `gateway.circuit_breaker.opened.v1`). |
| Audit event | The `correlation_id` envelope field is the same value. |
| Log MDC | Put under key `requestId`; every log line in the request scope carries it. |
| OTel | Bound to the root span as the attribute `platform.request_id`. The OTel `trace_id` (W3C `traceparent`) is **distinct from** the request id. |
| Retry | The id is **stable** — a retried request keeps the same id; the audit topic is partitioned by `correlation_id` so the same request id lands on the same partition and is processed in order. |

## 7. Distributed Tracing

- OpenTelemetry SDK auto-instruments HTTP, the Redis client,
  and the Kafka producer.
- One root span per request named `{METHOD} {route}` (e.g.
  `POST /v1/rides`).
- Child spans for: JWT verify, Redis `SISMEMBER` (revocation),
  Redis `INCR` (rate limit), upstream HTTP call, Kafka audit
  publish, JWKS cache lookup.
- `traceparent` is propagated to the upstream call and to the
  Kafka producer headers.
- Sample rate: 100% on errors and rate-limit rejections; 10%
  on success in production; 100% in staging.
- The audit event includes `trace_id` so a log search for a
  trace id surfaces the corresponding audit event and vice
  versa.
- The W3C `traceparent` is **distinct from** the request id
  (see [ADR-0019](../../architecture/adrs/0019-request-id-at-the-edge.md)).
  The request id is the OTel attribute `platform.request_id` on
  the root span; the trace id is the W3C `trace_id`. A single
  request has one request id and one trace id, but they are not
  the same value. The request id ties a log line, an audit event,
  a downstream call, and a Kafka message together; the trace id
  opens the trace UI.


## Downstream isolation

This section describes how this service handles failures in
its upstream and downstream services. The platform-wide
isolation playbook — including the per-class (CRITICAL /
DEGRADABLE / BEST-EFFORT) behavior, the dependency matrix,
and the configuration knobs — is in
[`../../architecture/SERVICE_ISOLATION.md`](../../architecture/SERVICE_ISOLATION.md).
The canonical error-code catalog and propagation rules are in
[`../../architecture/DOWNSTREAM_ERROR_CATALOG.md`](../../architecture/DOWNSTREAM_ERROR_CATALOG.md).

When this service's own code fails unexpectedly, it returns
`500 INTERNAL_ERROR`. When an error originates from another
service, this service follows the propagation rules in
[`DOWNSTREAM_ERROR_CATALOG.md` 5](../../architecture/DOWNSTREAM_ERROR_CATALOG.md)
(forward verbatim, translate, degrade, or reject) and includes
a `downstream` block identifying the original source.

### Per-downstream configuration

Per-downstream timeout / bulkhead / circuit / retry / fallback
configuration lives in the service's application config
(Kotlin: `application.yml` under `platform.outbounds.*`;
Go: `internal/outbounds/manifest.yaml`). The shared library
(`platform-spring-boot-bulkhead` for Kotlin, `internal/bulkhead`
for Go) reads the manifest and wires up the isolation pattern.

### Error envelope

Every error response uses the platform envelope defined in
[`../../shared/CONVENTIONS.md` 1](../../shared/CONVENTIONS.md)
(RFC 7807 + `downstream` block). The codes this service emits
are in 1 of this document; the canonical catalog is in
[`DOWNSTREAM_ERROR_CATALOG.md`](../../architecture/DOWNSTREAM_ERROR_CATALOG.md).
