# Super Admin permission to access all services — implementation plan

## Goal

Give operators a way, through `admin-service`, to grant and revoke
**super admin access to every service in the platform** for a given
admin user (a `SUPER_ADMIN` preset bundle = `platform.super_admin` + all
58 `<service>.admin` scopes), with break-glass co-signature, full audit,
and a service-catalog endpoint so operators can browse what they're
granting.

The platform already accepts `platform.super_admin` in every service's
`TECH.md` §10.1. This work adds the **management surface** for that role
and makes the SUPER_ADMIN bundle **explicit** in every service's docs.

## Scope decisions (locked from user answers)

- **SUPER_ADMIN bundle = `platform.super_admin` + 58 `<service>.admin` scopes** (api-gateway.admin included).
- **All grant/revoke flows route through `identity-service`**, which calls Keycloak (it is the platform's sole authorized Keycloak admin caller per `identity-service/README.md` §12).
- **Every grant/revoke of `platform.super_admin` requires break-glass co-signature** (mirrors SEC--004 / SEC--005).
- **A new §10.7 will be appended (not renumbered) to every service's `TECH.md`** stating explicit SUPER_ADMIN bundle membership.

## Files to change

### A. `identity-service` — new endpoints to grant/revoke roles

`identity-service` gains 2 inbound admin endpoints so `admin-service`
can manage Keycloak realm-role assignments without bypassing the
"identity-service owns Keycloak" rule.

**`docs/services/identity-service/INTEGRATION.md`**
- §1 (new inbound entries, before §1.1 or as §1.10+):
  - `POST /admin/v1/identities/{id}/roles/{role}` — grant a realm role to a Keycloak user.
    - Auth: `platform.super_admin` (or `platform.admin` for non-`platform.super_admin` roles).
    - Body: `{ "reason_code": "...", "preset": "SUPER_ADMIN" | null }`.
    - 200 returns the updated user payload.
    - 403 `BREAK_GLASS_REQUIRED` if `role == "platform.super_admin"` and no co-signer in `X-Break-Glass-Cosigner`.
    - 409 `ROLE_ALREADY_ASSIGNED`.
  - `DELETE /admin/v1/identities/{id}/roles/{role}` — revoke.
    - Same auth + break-glass rules as grant.
    - 404 `ROLE_NOT_ASSIGNED`.
  - `GET /admin/v1/identities/{id}/roles` — list a user's realm roles.
    - Auth: `platform.admin` (read-only; no break-glass needed).
- §2 (outbound table): add 3 Keycloak admin rows
  - `POST /admin/realms/{realm}/users/{id}/role-mappings/realm`
  - `DELETE /admin/realms/{realm}/users/{id}/role-mappings/realm`
  - `GET /admin/realms/{realm}/users/{id}/role-mappings/realm`
  - with the standard 2s timeout / 2 retries / exp backoff / circuit-breaker columns.
- §3 (events): add `identity.role.granted.v1` and `identity.role.revoked.v1` to the published-events table.

**`docs/services/identity-service/ERD.md`**

- Add new fields to `identity_audit_log`: `role TEXT NULL`, `preset TEXT NULL` (e.g. `"SUPER_ADMIN"`), `cosigner_id UUID NULL`, `break_glass BOOLEAN NOT NULL DEFAULT false`.
- Add a new section §3.7 `RoleAssignmentHistory` (append-only) capturing every role grant/revoke for permanent audit, mirroring `PricingGeoConfigHistory` in `admin-service/ERD.md` §3.7.

### B. `admin-service` — operator-facing management endpoints

The operator-facing endpoints live in `admin-service` and follow the
existing `POST /v1/admin/{service}/{action}` dispatch pattern from
WORKFLOWS §1.11. They wrap the new identity-service endpoints and add
the audit / reason / signature / break-glass / IP-allowlist / MFA
checks from SECURITY_ARCHITECTURE §14.

**`docs/services/admin-service/INTEGRATION.md`**
- §1 (new inbound entries):
  - `POST /v1/admin/identity/grant-super-admin` — grants `platform.super_admin` + the 58 `<service>.admin` scopes (= `SUPER_ADMIN` preset). Body: `{ "user_id": "...", "reason": "...", "preset": "SUPER_ADMIN" }`. Auth: `platform.super_admin` + break-glass + `X-Signature` + `X-Audit-Reason` + MFA + IP allowlist. Forwards to `identity-service POST /admin/v1/identities/{id}/roles/platform.super_admin` plus 58 grant calls (or one bulk-grant if identity-service accepts a list — see open question below).
  - `DELETE /v1/admin/identity/revoke-super-admin` — revokes `platform.super_admin` and the 58 `<service>.admin` scopes. Same auth as grant.
  - `GET /v1/admin/identity/permissions/{user_id}` — list a user's current roles + their preset membership.
  - `GET /v1/admin/services` — **service catalog** endpoint. Returns all 58 services with their declared admin scopes (the `DB` column from RECOMMENDATIONS §2 + the roles from §10.1 of each TECH.md). Used by the operator UI to show "what does SUPER_ADMIN grant access to?". Auth: `platform.admin` (read).
  - `GET /v1/admin/presets` — list available permission presets (currently just `SUPER_ADMIN`).
- §2 (outbound to identity-service): 3 new calls documented.
- §3 (events produced): add `admin.super_admin.granted.v1`, `admin.super_admin.revoked.v1`.

**`docs/services/admin-service/WORKFLOWS.md`**
- New §5 "Super Admin Grant / Revoke" workflow:
  1. Operator (must already hold `platform.super_admin`) opens the catalog at `GET /v1/admin/services`, sees the 58 services listed with their admin scopes.
  2. Submits `POST /v1/admin/identity/grant-super-admin` with `user_id`, `preset=SUPER_ADMIN`, reason ≥ 8 chars, signature.
  3. Service validates: actor has `platform.super_admin`, IP in super-admin allowlist, MFA claim present, request signed, time-of-day check (off-hours requires co-signer).
  4. Service writes a `SuperAdminGrant(action='grant', actor_id, cosigner_id, ...)` row.
  5. Service calls `identity-service POST /admin/v1/identities/{user_id}/roles/{role}` for `platform.super_admin` and each of the 58 `<service>.admin` roles.
  6. identity-service publishes `identity.role.granted.v1` × 59; `admin-service` publishes `admin.super_admin.granted.v1`.
  7. Service returns 200 with the updated permission set.
- Failure paths: `CO_SIGNER_REQUIRED`, `BREAK_GLASS_REQUIRED`, `IP_NOT_ALLOWED`, `MFA_REQUIRED`, `SIGNATURE_INVALID`, `AUDIT_REASON_REQUIRED`.

### C. Per-service `TECH.md` — append a §10.7 to all 58 services

Append (do **not** renumber; the existing §11 deep-links stay intact) a new section at every service's `TECH.md`:

```markdown
### 10.7 Super Admin preset membership

This service is included in the platform's `SUPER_ADMIN` permission
preset. An operator granted the preset receives:

- The platform-wide guard role `platform.super_admin`.
- This service's per-service admin role `<service>.admin`.

Grant and revoke are managed through
[`admin-service`](../admin-service/TECH.md#10-admin-endpoints--rbac)
via `POST /v1/admin/identity/grant-super-admin` and
`DELETE /v1/admin/identity/revoke-super-admin`. Both require
break-glass co-signature and emit `audit.admin.<service>.v1` (per
§10.2) for each touched record.
```

The `<service>.admin` role name is derived per-service from the
service directory name (e.g. `payment-service` → `payment.admin`,
`api-gateway` → `api_gateway.admin` to match Keycloak's
underscored role convention). The script that produces the 58 edits
uses the directory name → role mapping.

This is appended **after** the existing §10.6 `Local admin (dev only)`,
so the existing §10.1..§10.6 numbering stays untouched. The next §11
"Open-source bundle" deep-link (`TECH.md#11-open-source-bundle`) is
preserved because we only appended.

## Open question (will ask before implementing the identity-service side)

- Should `identity-service` expose a single bulk grant endpoint
  `POST /admin/v1/identities/{id}/roles` accepting `{ roles: [...] }`
  to grant all 59 roles in one call, or should `admin-service` loop
  over 59 single-role grants? Bulk is faster + atomic, but is a wider
  surface. Recommendation: bulk endpoint, behind the same
  break-glass gate.

## Risks / things to flag in PR description

- **Bulk role grants** touch 59 Keycloak admin calls. On failure mid-grant we need idempotent retry or compensation (delete what was added). The plan above calls this out under the open question.
- **Audit fan-out**: each grant produces 59 `identity.role.granted.v1` events + 1 `admin.super_admin.granted.v1`. audit-service consumers should be ready for the spike.
- **No FK from `admin.super_admin_grant.user_id` to `identity-service`** — same rule as the rest of `admin-service/ERD.md` §2.
