## Plan: WhatsApp channel + plug-in provider model for notification / communication-gateway

### Goal

Extend the existing **notification-service** and **communication-gateway-service** docs to add **WhatsApp as a new channel**, document a **generic plug-in provider contract** (so any future provider — Telegram, RCS, Slack, in-app push, etc. — can be onboarded without schema rewrites), introduce a `whatsapp` template body structured model for provider-approved templates, ship an immutable `template_history` audit table + `template_version_snapshot` on deliveries, and deliver an English + Arabic template seed catalog with a Mermaid template-rendering demo.

The deliverable is **Markdown documentation only**, consistent with the rest of the repository — no code changes, just architecture/contract/spec.

### Approach (high-level)

1. **Extend both existing service doc sets in place** rather than creating a brand-new service. WhatsApp becomes a first-class sibling of `sms`, `email`, `push` in the gateway, and a sibling of `push`, `sms`, `email`, `in_app` in notification orchestration. (The user explicitly chose this path.)
2. **Defer provider selection** — define a generic plug-in provider contract (capabilities, credentials, webhook signature, template-approval flow, rate-limit shape, regional routing) instead of pinning to Twilio/Meta/360dialog.
3. **Strengthen audit** — add `notification.template_history` (immutable, append-only, records every version + approver + diff summary) and an explicit `template_version_snapshot_id` column on `notification.deliveries` so each delivery is bound to the exact template bytes that were rendered.
4. **Document a `whatsapp` template body model** in `notification.templates` because WhatsApp's provider-approved templates are structured (header + body + footer + buttons + variables) — not a single TEXT body like SMS/email/in-app. Backwards compatible: existing `body` and `subject` columns are kept; a new optional `body_structured JSONB` column carries WhatsApp templates, plus a `template_type TEXT` discriminator.
5. **Seed catalog + Mermaid demo** — a JSON seed with 12 template names × 4 non-WhatsApp channels × 2 locales (en, ar) plus the same 12 names × `whatsapp` × 2 locales with the structured WhatsApp body, plus a Mermaid sequence diagram showing en→ar locale fallback + WhatsApp template approval + render → send → delivered.

### Design details

#### Channel model — single canonical list, per-tier

| Layer | Channels |
|-------|----------|
| **notification-service orchestration** (5) | `push`, `sms`, `email`, `in_app`, `whatsapp` |
| **communication-gateway-service transport** (4) | `sms`, `email`, `push`, `whatsapp` |
| **Provider plug-in taxonomy** (open) | any provider that satisfies `WHATSAPP_PROVIDER_CONTRACT.md` capability matrix |

`in_app` stays in notification-service only — same as today.

#### `notification.templates` extension

| New column | Type | Default | Purpose |
|------------|------|---------|---------|
| `template_type` | TEXT NOT NULL | `'plain'` | `plain` \| `whatsapp_structured` — discriminator |
| `body_structured` | JSONB NULL | — | `{ header, body, footer, buttons[], variables[] }` for WhatsApp; null for others |
| `provider_template_id` | TEXT NULL | — | the provider's pre-approved template id (nullable until provider approves) |
| `provider_template_language` | TEXT NULL | — | `en`, `ar`, etc. — distinguishes from logical `locale` |
| `provider_template_status` | TEXT NULL | — | `draft`, `submitted`, `approved`, `rejected`, `paused` |
| `provider_template_approved_at` | TIMESTAMPTZ NULL | — | once approved, used for the 24h window anchor |

Backward compatible: existing rows keep `template_type='plain'`, `body_structured=NULL`.

#### New `notification.template_history` table (immutable)

| Column | Type | Purpose |
|--------|------|---------|
| `id` | UUID PK | snapshot id — also referenced from `deliveries.template_version_snapshot_id` |
| `template_id` | UUID | the logical template |
| `version` | INT | the version this row materialises |
| `name` | TEXT | denormalised for query simplicity |
| `channel` | TEXT | denormalised |
| `locale` | TEXT | denormalised |
| `subject` | TEXT NULL | |
| `body` | TEXT | |
| `body_structured` | JSONB NULL | |
| `template_type` | TEXT | |
| `provider_template_id` | TEXT NULL | |
| `provider_template_status` | TEXT NULL | |
| `provider_template_approved_at` | TIMESTAMPTZ NULL | |
| `metadata` | JSONB NULL | |
| `required_variables` | TEXT[] | |
| `diff_summary` | JSONB NULL | `{ added_variables[], removed_variables[], body_changed:bool, structure_changed:bool, approver_sub, approved_at }` |
| `published_by` | UUID | Keycloak `sub` of publisher |
| `approved_by` | UUID NULL | for WhatsApp — separate from publisher |
| `created_at` | TIMESTAMPTZ NOT NULL | |
| `revision_no` | INT NOT NULL | monotonically increasing per `template_id` for ordering |

Append-only — no UPDATE/DELETE allowed; enforced via a row-level check trigger documented in `TEMPLATE_HISTORY.md`.

#### `notification.deliveries.template_version_snapshot_id`

| Column | Type | Notes |
|--------|------|-------|
| `template_version_snapshot_id` | UUID NULL | FK-style reference (no actual PG FK) to `notification.template_history.id`; gives each delivery a tamper-evident pointer to the exact bytes rendered |
| `rendered_template_version` | INT NULL | denormalised version number for analytics |

Existing `template_id` column retained. Together they let support reconstruct "what was this customer actually sent?" without ambiguity.

#### Generic provider plug-in contract

Documented in `WHATSAPP_PROVIDER_CONTRACT.md`:

| Capability | Required? | Notes |
|------------|-----------|-------|
| `send_template(template_name, variables, language, recipient)` | yes | |
| `send_freeform(within_24h_window)` | optional | only within 24h of user's last inbound msg |
| `media_upload(reference_type, ref)` | yes | for header media |
| `template_submit(name, language, components)` | yes | submit for approval |
| `template_status(template_id)` | yes | poll for `approved`/`rejected` |
| `webhook_signed(event_types[])` | yes | HMAC-SHA256 (provider-specific header e.g. `X-Hub-Signature-256`) |
| `health_metrics` | yes | p50/p95/p99 + error rate |
| `regional_routing(country_code)` | optional | for Meta Cloud + 360dialog |
| `optout_keyword_stop` | yes | registers STOP keyword on template |
| `template_deletion` | yes | for admin delete |

The contract is **WhatsApp-shaped but provider-agnostic** — anyone implementing it can be onboarded by inserting a row into `comms_gateway.providers` + a row in Vault. Zero schema changes to add a provider. This also future-proofs Telegram, RCS, etc.

#### Mermaid rendering demo (`RENDERING_DEMO.md`)

Three diagrams:

1. **Sequence — happy path**: `event in → render ar template → fallback to en if ar missing → channel selection (push+sms+whatsapp+email) → POST /v1/sends (channel=whatsapp) → Meta Cloud ack → webhook delivered → state updated → notification.sent.v1 emitted`.
2. **Sequence — WhatsApp approval workflow**: `admin POST /v1/admin/templates {channel:whatsapp} → submission to provider → provider status webhook → publish atomic across en+ar+whatsapp`.
3. **State diagram — `template_history` lifecycle**: `draft → submitted → approved | rejected → paused → retired`.

Plus two rendered output previews (en + ar) of `trip.completed` for both `email` (Handlebars) and `whatsapp` (structured) formats.

### Acceptance criteria for this work

- Every CHECK constraint extension is documented with the exact migration line so a DBA can run it.
- The `notification.deliveries` audit chain is end-to-end: `template_id` → `templates.version` → `template_history.id` → `deliveries.template_version_snapshot_id` is reconstructable.
- A future provider can be onboarded with **zero schema changes** — only an admin POST + a Vault entry.
- The seed catalog covers all 4 documented event categories (trip, food, payment, safety) plus marketing/loyalty/merchant/courier/driver/incentive/support to exercise the full template matrix.
- en + ar locales are present in the seed for every (name, channel) combination.
- WhatsApp templates in the seed have the exact structured shape (header/body/footer/buttons + variable index mapping) used in production WhatsApp Business API.
- The plan is fully implemented in documentation; **no code or config is changed**, only `.md` and one `.json` seed file.

### Out of scope

- No actual provider credentials or vendor-specific code.
- No migrations applied — just migration documentation in the ERD sketches.
- No changes to `user-profile-service` notification preferences (the preferences table in `notification-service` already has `channel` and is extended; user-profile's notification_preferences JSONB can be extended in a follow-up if you want — flag if you do).
- No changes to the runtime/technology choice (Node 20 vs Go vs Spring remains a pre-existing inconsistency that the user already flagged elsewhere — not addressed here).
