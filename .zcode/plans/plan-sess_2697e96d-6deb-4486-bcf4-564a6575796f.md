# Open-source Integration — Implementation Plan

## Goal

Add an **open-source integration** layer to the docs-only microservices deliverable so that every service can be lifted out as a standalone project *or* run as part of the platform without changes. The user wants:

1. **Platform-wide OSS attribution** (projects + libraries + license attribution).
2. **Per-service extractability** — each service can run as a standalone project, with notes identifying which dependencies are platform-required vs. optional.
3. **Skeleton** — a minimal dependency-manifest stub per service so the "lift out" claim is concrete.

The user picked the **"single platform-wide doc + cross-refs"** shape for the attribution catalogue, and **"both — notes + skeleton"** for the extractability piece.

---

## Document conventions to follow (verified)

- **Single source of truth**: every per-service doc already says "All pinned versions are in `../RECOMMENDATIONS.md` §5 — never pin versions directly here". The new attribution docs must obey the same rule.
- **Section numbering**: per-service docs use `## 1.`, `## 2.`, … `## 10.` for TECH.md; `## 1.` … `## 18.` for README.md; external numbering (e.g. `## 11.`) is allowed when it's appended to a specific service (e.g. fraud-risk-service has `## 19. Accounting impact`).
- **"See also" footer**: every service doc ends with a "See also" block listing sibling docs + platform-wide docs. The new attribution doc must be added to this footer everywhere.
- **Reading order**: `docs/README.md` has a numbered Reading Order table the new docs must slot into.
- **No existing OSS / NOTICE / LICENSE / SPDX plumbing** — this is the first such deliverable.

## Deliverables

### 1. New platform-wide doc: `docs/shared/OSS_DEPENDENCIES.md` (≈ 350 lines)

The single source of truth for OSS attribution. Lives next to `PLATFORM_BASELINE.md` since both are referenced by every service.

**Sections:**
1. Purpose & scope (one paragraph: this doc is the platform-wide OSS catalogue; service-specific OSS bundles live in §6 of each service's TECH.md).
2. Platform-wide OSS projects (the major infrastructure pieces — PostgreSQL 18, Kafka 3.9, Keycloak, Redis 7.x, OpenSearch, Istio, Envoy, OpenTelemetry, Prometheus, Grafana, Loki, Tempo, Jaeger, Fluent Bit, Vault, postGIS, Apicurio, etc.) — table with: project / version pin / SPDX license / where it's used (services list) / license-text URL.
3. Kotlin / Spring Boot OSS dependencies (the 18 libraries from `RECOMMENDATIONS.md` §5.1) — table with: library / pinned version / SPDX license / Maven coordinate / why-we-need-it.
4. Go OSS dependencies (the 10 libraries from `RECOMMENDATIONS.md` §5.1) — table with: library / pinned version / SPDX license / import path / why-we-need-it.
5. Python OSS dependencies (the 15 libraries from `RECOMMENDATIONS.md` §5.1) — table with: library / pinned version / SPDX license / PyPI package / why-we-need-it.
6. Optional Rust inner loop (the 3 libraries) — same shape.
7. Per-service OSS bundle index — a 58-row table mapping each service to (a) its language profile, (b) the libraries it pulls in by name (cross-reference to the per-language tables), (c) its external vendor SDKs (from `RECOMMENDATIONS.md` §2 column "External"), (d) the platform-required services it depends on at runtime. This is the **canonical mapping** that every service's TECH.md `/ 6. Open-source bundle` will reference.
8. License attribution & NOTICE file guidance — what each service bundle must carry (per the standard Spring Boot / Go / Python NOTICE practice), how to regenerate the third-party licence list at build time (`gradle-license-report`, `go-licenses`, `pip-licenses`).
9. License compatibility matrix — short prose on the stack's compatibility (GPL-2.0 PostGIS is dynamic-linked plugin, Hibernate LGPL-2.1, AGPL-3.0 Grafana/Loki are runtime-only at the observability tier → safe for an internal SaaS; the boundary that would change the analysis is *distributing* the binaries).
10. See also — link to `PLATFORM_BASELINE.md`, `RECOMMENDATIONS.md`, every per-service `TECH.md`.

### 2. New per-service section: `## 6. Open-source bundle` added to each of 58 `TECH.md` files

A short, **service-specific** section (~30 lines) that:
- States the language profile (already known from `RECOMMENDATIONS.md`).
- Lists the **service-specific external vendor SDKs** (the "External" column from `RECOMMENDATIONS.md` §2 — payment providers, SMS, map providers, push, etc.) — these are the only OSS-adjacent items that vary per service.
- Lists the **2–4 most important runtime OSS dependencies** that this service actually exercises (subset of the per-language table in `OSS_DEPENDENCIES.md`).
- Includes an **Extractability** sub-section: which dependencies are platform-internal (platform-spring-boot-starter, Keycloak, the config-service) and which are swappable (PostgreSQL → H2 for tests, Keycloak → stub JWT verifier, Redis → in-memory cache, Kafka → in-process channel).
- Adds a Pointer to the skeleton (Deliverable 3) and to `OSS_DEPENDENCIES.md`.

The new section uses the existing TECH.md §6 heading slot. We will renumber §6 Security → §7, … §10 Admin endpoints → §11. Every other internal anchor in any service doc that references TECH.md `§6` (currently "Security") would need patching — but the platform-wide convention is to refer to §6.7 and similar in the wider `RECOMMENDATIONS.md` not to specific TECH.md sections, and per-service docs cross-reference by file not by section number. The Read-grep confirms: **no internal link to `TECH.md#6` exists anywhere** — using `## 6. Open-source bundle` and renumbering downstream is safe.

### 3. New per-service skeleton: `docs/services/<service>/SKELETON.<ext>` file (58 files)

The minimum dependency manifest that proves a service can be lifted out. One file per service, extension chosen by language:
- **Kotlin (46 services)** → `build.gradle.kts` skeleton
- **Go (8 services)** → `go.mod` skeleton
- **Python (4 services)** → `pyproject.toml` skeleton

Each skeleton is **~15–30 lines** that:
- Declares the language runtime (Kotlin 2.2, Go 1.25, Python 3.14).
- Declares the platform-internal vs swappable dependencies with comments.
- Shows the *one* external vendor SDK (payment provider, map provider, etc.) as a placeholder with a clear "swap or stub" comment.
- Has a `// FOR PLATFORM-RUN: see docs/shared/OSS_DEPENDENCIES.md` header pointing at the catalogue.

These skeletons are documentation, not runnable code — they're explicitly labelled as such. The point is to show the *shape* of an extracted version, not to write a working build.

## Risks & mitigations

1. **Renumbering TECH.md sections (Security 6 → 7, etc.)** could break a deep-link. Mitigation: grepped already; no internal `TECH.md#6` references exist. External readers landing on `#7-security` would break — but the existing convention is to point to `RECOMMENDATIONS.md` §6 for admin/RBAC, not back to TECH.md. **Phase A** will add a grep verification step before any renumbering.

2. **Sparse licence information for some libraries** (e.g., some Python packages' translations of GPL). Mitigation: cite the official upstream LICENSE link in each row; if the SPDX is debated, mark the row `SPDX: <license> (verify upstream)`.

3. **Skeletons are not runnable** — could mislead future maintainers into thinking they bootstrap a service. Mitigation: every skeleton's first line is a comment: `# SKELETON ONLY — documentation, not a working build. See ../TECH.md for the platform-default setup.`

4. **Vault was BUSL-1.1 (source-available)**, not OSI-approved open source. Mitigation: flag this in the platform-wide table with a "License class: source-available" column so the distinction is explicit.

5. **AGPL-3.0 services** (Grafana, Loki) — the platform uses them as observability backends, not as embedded libraries. Mitigation: row entry explicitly says "runtime-only, not linked into service binaries — acceptable for internal SaaS; would change if we distributed an on-prem appliance."

## Out of scope (explicit)

- No machine-generated dependency lockfile (`gradle.lockfile`, `go.sum`, `uv.lock`) — this is a docs-only deliverable; the skeleton shows the *shape*, not the actual resolved tree.
- No NOTICE file generation tooling — the catalogue describes what each service bundle must do, but does not produce a NOTICE.
- No SPDX document — the catalogue is human-readable Markdown.
- No changes to existing service logic, ERD, or workflows — only additive doc changes.
- No automated CI check — the deliverable is documentation; the platform's existing CI is not in scope.
