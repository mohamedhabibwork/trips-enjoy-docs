- **Rationale & Regulatory Mandate:** Under Saudi ZATCA Phase 2 (*Fatoora*), any VAT-registered platform issuing subscription invoices (`B2B` to Saudi organizations, `B2C` to Saudi travelers/suppliers) or acting as billing agent must generate cryptographically stamped XML invoices with chained `ICV` (Invoice Counter Value) and `PIH` (Previous Invoice Hash). Launching `SA` in P5 with plain PDFs creates immediate regulatory exposure.
- **Data Contract:** Store `tax_authority_uuid`, `icv_seq`, `prev_invoice_hash`, `qr_tlv_base64`, `xml_storage_key`, and `clearance_status` (`not_applicable`, `pending_report`, `reported`, `cleared`, `rejected`) in `invoices` metadata/columns. Preserve `D-179`: if ZATCA clearance/reporting fails transiently, the traveler booking stays `Confirmed` while the outbox worker retries 3 times before routing to Finance review.
- **Trade-offs:** Building direct ZATCA CSID onboarding takes ~2–3 sprints vs using a certified Saudi middleware (e.g., *Wafeq* / *Marmin* / *ClearTax MENA*). **Recommended:** integrate via a certified ZATCA Phase 2 API gateway behind `TaxComplianceAdapter` for P5 launch speed, keeping cryptographic hashes and XML archives in our own S3 WORM bucket.
